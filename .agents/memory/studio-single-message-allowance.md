name: Studio temporary generation policy
description: Temporary Studio outputs; later two-creation website offer permits minimal purchase/session counts only.
---

Santa Studio should generate from Mark's source audio, let the user play and
download the MP3, then retain no generated audio or generation history.
Do not reconnect the retired generation/archive tables, correction allowances,
identity locks or reload recovery. The later website offer permits minimal
two-success accounting per canonical £6.50 purchase, and two per authorised
visitor session for the owner-selected shared voucher only.

**Why:** The owner explicitly superseded the earlier two-success/correction
requirement: “We don't need to store any mp3's just allow the user to generate
the file, and click save. Thats it. We don't need to keep a record of anything
or hold audio anywhere.”

**Why:** The owner subsequently explicitly chose two successful creations per
website purchase, superseding only the ban on minimal success counts. This
does not permit audio, recipient, choice or download history.

**How to apply:** Preserve genuine voucher/payment checks, expiry and abuse
protection. Use the verified canonical purchase, not a replaceable credential.
Limited shared-voucher sessions are independent visitors, not lifetime
entitlements. Other vouchers and native purchases keep their existing rules.
Tell users to download before leaving or refreshing; temporary outputs
cannot be recovered. Keep required allowance storage fail-closed at runtime
and out of website compilation; production schema changes need separate approval.

Select the limited voucher by a non-secret slot marker, never by committing or
documenting an access-code value.

**Why:** Source and collaborator-visible documentation are not credential stores.

**How to apply:** Keep actual voucher values exclusively in secure configuration;
if a credential needs rotation, coordinate the resulting session invalidation
with the owner instead of silently changing live access.

Verified website paid access takes precedence over any old voucher in the
same browser, including when the paid allowance is exhausted. Never show
voucher values in the customer Studio UI.

**Why:** The owner found an already-paid journey selecting old voucher access
and explicitly required the existing paid allowance to remain exactly two
successful creations, with valid voucher-only journeys preserved.

**How to apply:** Treat access selection as a server entitlement rule as well
as browser presentation. Checkout return, reload and Start Again must keep the
same verified purchase allowance; do not reset counters or infer paid usage
from older voucher activity.

After both messages are used, Start Again should look disabled and only open
a limit/download reminder, never a discard-and-restart confirmation.

**Why:** The owner asked for a greyed-out control and a reminder to download
and keep the files before closing the tab or leaving the site.

**How to apply:** Preserve existing recordings and downloads. Pointer and
keyboard activation may explain the limit but must not clear or reset anything.
